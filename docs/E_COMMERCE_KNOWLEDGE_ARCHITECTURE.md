## 1. 核心定位

DevWiki 以 C#／.NET 後端知識為基礎，提供三個互相連結的學習入口：「深入學習 .NET」「跟著製作電商」「部署與維運系統」。讀者可以依技術查閱、按知識深度進修，也可以沿著同一個案例理解從程式到正式運作的責任。

使用者列出的十個領域成為完整知識地圖，保留六個 P0 領域與四個 P1 領域。它涵蓋 C#、ASP.NET Core、資料存取、Infrastructure、Runtime 與工程實務，採「C#／.NET 後端知識地圖」作為入口名稱。各領域的必學項目、既有涵蓋程度與深入學習目標，見 [C#／.NET 深入學習地圖](CSHARP_DOTNET_LEARNING_MAP.md)。

Kubernetes 與 GKE 另設 [雲端部署與維運知識地圖](CLOUD_NATIVE_LEARNING_MAP.md)，涵蓋容器、網路、編排、平台、交付與運作。D08 Infrastructure 繼續負責程式如何使用 HTTP、Redis、RabbitMQ 與背景服務；雲端地圖負責這些程序和依賴如何部署、取得權限與維運。

這些順序是新增的雲端學習提案，與原本 .NET 十大領域的 P0／P1 分開記錄。

同一個概念維持一篇主要知識文章。電商章節引用這些文章，負責串接需求、商業規則、流程與取捨；實作指南負責環境準備與操作。

寫作遵循五個原則：

1. 先說明使用者想完成什麼，再引出技術問題。
2. 任一篇文章都提供理解範例所需的局部背景。
3. 技術文章保留可重用的概念與最小範例。
4. 案例、程式碼與操作指令使用相同的名稱與資料。
5. 文章中的可執行範例、示意片段與專案操作各自明確標示。

## 2. 共同案例的範圍

### 第一階段：完成一間商店的購買流程

以蝦皮常見的瀏覽、購物車與下單情境幫助讀者理解，教學案例自行定義規則。第一階段採單一商店，角色為買家與店主，知識重心放在後端。

| 功能範圍 | 教學案例要支援的行為 |
| --- | --- |
| 商品 | 店主建立與修改商品；買家查詢、篩選與分頁 |
| 身分與權限 | 辨識買家與店主；買家只能查看自己的訂單 |
| 購物車 | 加入商品、修改數量、移除商品與計算預估金額 |
| 訂單 | 依下單當時的價格建立明細，保存成交價格快照 |
| 庫存 | 下單時檢查並扣減庫存，處理多人同時購買 |
| 付款 | 用模擬付款結果說明狀態轉換與重複請求 |
| 通知 | 分別說明訂單建立通知、付款成功通知與背景處理 |
| 品質 | 驗證正常流程、失敗、重送與故障恢復，並能追查處理經過 |

這是目標案例範圍。目前實驗程式已有商品查詢與價格更新、Redis 快取、訂單與 Outbox、Worker、Inbox 與模擬通知；購物車、完整訂單明細、庫存、買家權限與付款流程需要另行補寫。

### 第二階段：擴展為多商家平台

後續依學習需求擴充商店與商品歸屬、多商家拆單、優惠券、取消與退款、庫存預留及到期釋放、評價、物流與聊天。這些功能進入內容規劃時，再補充對應的商業規則與先備知識。

前端可成為後續獨立知識分支，沿用同一套案例，說明畫面、表單、登入狀態與 API 整合。第一階段文章以使用流程圖、API 請求與結果說明畫面背後的行為。

### 部署案例的範圍

先使用同一份模組化後端與 Worker，逐步走過主機執行、Docker Compose、本機 Kubernetes、GKE 與自動化交付。API 和 Worker 有各自的部署及擴縮需求，業務模組仍可維持在同一個後端應用。

雲端起步先學 API／Worker 的部署與外部服務連線，再另設有狀態服務的深入篇。資料庫採 Cloud SQL PostgreSQL 作為主要提案；Redis 先說明雲端端點與產品能力差異；RabbitMQ 保留原有訊息語意，比較代管服務與 Kubernetes Operator 的責任。實際供應商、區域與費用在實作前確認。

目前根目錄 Dockerfile／Compose 用於 Wiki 靜態網站；電商實驗的 API／Worker 仍需補容器映像與部署設定。網站本身的交付和電商案例的交付各自說明。

部署路徑採「容器 → 本機 K8s → GKE → 自動化交付 → 維運深化」。新網路範例優先解釋 Gateway API，同時比較既有 Ingress 的使用背景；Ingress API 已凍結，Kubernetes 官方建議使用 Gateway API。[Kubernetes Ingress](https://kubernetes.io/docs/concepts/services-networking/ingress/)。

GKE 起步以 Autopilot 叢集為主要提案，再深入 Standard 的節點與排程控制；目前 Standard 叢集也能執行 Autopilot 工作負載，文章需分清「叢集模式」與「工作負載管理方式」。[GKE 模式選擇](https://docs.cloud.google.com/kubernetes-engine/docs/concepts/choose-cluster-mode)。

## 8. 文章格式與獨立閱讀標準

### 技術知識篇

1. 本篇問題與讀完能理解的事情。
2. 三到五句的局部案例背景：角色、資料、元件與目前步驟。
3. 原理與資料／處理流程。
4. 最小完整範例，或清楚標示用途的示意片段。
5. 預期結果、常見錯誤與取捨。
6. 電商情境篇、實作指南、先備知識與官方來源連結。

例如「Redis 資料型別、Key 與 TTL」保留技術標題，先交代資料庫是商品資料來源、Redis 保存副本，再用一個商品 Key 解釋保存、讀取與過期。

### 電商情境篇

1. 使用者需求與具體例子。
2. 商業規則、成功條件與失敗結果。
3. 涉及哪些資料與元件，以及各自責任。
4. 先採用的方案，後續需求增加時如何演進。
5. 指向需要理解的技術知識篇。
6. 可選擇跟做的實作指南與檢查點。

例如「商品改價後，買家為什麼還看到舊價格？」串接 Cache-Aside、TTL、失效與並行回填，而各技術概念集中於主要知識文章維護。

### 實作指南

1. 本次要重現的流程，以及已完成的章節檢查點。
2. 專案取得方式、版本、工具與必要服務。
3. 命令執行的目錄、終端機、程序與先後順序。
4. 每項命令的用途、可觀察結果、成功與失敗判定。
5. 原始程式的位置、自訂輔助類別的責任與核心片段。
6. 停止、保留資料、重設及排錯方式。

命令區塊明確標示執行位置，例如「主機終端機」「Redis CLI」「API 請求」。`pnpm lab:*` 說明為此儲存庫的操作捷徑，並列出實際啟動的 .NET 程式或 Docker 服務。SDK 的類別與教學專案自訂類別分別介紹；複製即可執行的範例包含宣告、連線與必要設定。

| 層級 | 目的 | 指南必須交代 |
| --- | --- | --- |
