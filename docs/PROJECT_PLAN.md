## 1. 專案定位與目標

建立以繁體中文為主的軟體知識 Wiki，讓讀者可以依主題查詢概念，也能依學習路徑循序閱讀。第一階段集中建立 C# 知識，後續擴充 .NET、ASP.NET Core、其他程式語言與軟體工程主題。

網站以文章為核心，採用 Markdown／Git 維護內容，建置時產生靜態頁面與搜尋索引，再加入 PWA 的安裝與離線閱讀能力。

首期目標：

1. 提供分類清楚、可直接分享連結的 C# 知識文章。
2. 支援繁體中文與英文技術名詞的全文搜尋。
3. 提供手機、平板與桌面上的閱讀介面。
4. 支援 PWA 安裝與成功快取文章的離線閱讀。
5. 建立一致的文章格式、範例品質與更新流程。
6. 讓未來新增語言與框架時，可以沿用相同的內容模型。

### 1.1 規劃基準

| 項目 | 首期採用的規劃基準 |
| --- | --- |
| 讀者 | C# 初學者，以及需要快速查詢的軟體開發者 |
| 閱讀權限 | 公開閱讀 |
| 維護方式 | 主維護者編寫 Markdown，透過 Git 管理修改與發布 |
| 語言 | 繁體中文說明；程式碼、API 名稱與必要英文術語保留原文 |
| 內容規模 | 約 15 篇核心文章，加上主題入口與學習路徑 |
| 網站型態 | 以靜態頁面為主，互動功能逐步增加 |
| 首期發布方式 | 提供正式環境與預覽環境；託管平台於開始實作時選定 |

若閱讀權限改為私人，或初期即需要網站後台編輯，應在實作前調整內容來源、權限與部署設計。

## 3. 資訊架構與內容分類

### 3.1 全站分類

```text
軟體知識 Wiki
├─ 程式語言
│  └─ C#
│     ├─ 入門：環境、變數、型別、流程控制、方法
│     ├─ 型別與物件：class、struct、record、nullable
│     ├─ 物件導向：介面、繼承、多型
│     ├─ 資料處理：泛型、集合、LINQ
│     └─ 實務：委派、例外、資源管理、非同步與取消
├─ 平台
│  └─ .NET：執行環境、SDK、CLI、套件與專案管理
├─ 框架
│  └─ ASP.NET Core：Web API、DI、設定、資料存取
├─ 軟體工程
│  ├─ 測試
│  ├─ 設計原則與架構
│  └─ Git、建置與部署
└─ 學習路徑
   ├─ C# 入門
   └─ C# 到 ASP.NET Core（後續）
```

首期只開放已有內容的分類入口。預留分類不顯示為空白頁面。

### 3.2 組織原則

| 元素 | 職責 | 例子 |
| --- | --- | --- |
| 主題 | 區分語言、平台、框架與共通知識 | C#、.NET、ASP.NET Core |
| 分類 | 提供主題內的主要閱讀導覽 | 入門、物件導向、資料處理 |
| 標籤 | 連結跨分類的共同概念 | 非同步、效能、記憶體、例外 |
| 相關文章 | 說明具體的概念關聯 | async/await → CancellationToken |
| 學習路徑 | 為特定目標安排閱讀順序 | C# 入門 → 型別 → 物件 → 集合 |

同一概念以一篇主要文章維護。學習路徑與其他文章透過連結引用，避免內容複製後更新不同步。

| 頁面 | 建議網址 |

| 首頁 | `/` |
| C# 主題入口 | `/languages/csharp/` |

文章另外保留穩定的 `articleId`，供先備知識、相關文章與未來收藏功能引用。

## 4. 內容模型與編寫規範

### 4.1 文章資料

文章開頭以 YAML frontmatter 儲存資料，透過內容 schema 驗證。Starlight 支援 Markdown、MDX 與 frontmatter，Astro 的內容集合可提供資料驗證能力。[Starlight 內容編寫](https://starlight.astro.build/guides/authoring-content/)、[Astro Content Collections](https://docs.astro.build/en/guides/content-collections/)。

| 欄位 | 必要性 | 用途 |
| --- | --- | --- |
| `articleId` | 必填 | 全站唯一、發布後保持穩定的文章識別碼 |
| `title` | 必填 | 文章標題 |
| `description` | 必填 | 摘要與搜尋結果說明 |
| `slug` | 必填 | 穩定的公開網址 |
| `topic` | 必填 | 所屬主題，例如 `csharp` |
| `category` | 必填 | 所屬分類，例如 `async` |
| `tags` | 可選 | 跨分類概念與技術名詞 |
| `difficulty` | 必填 | `beginner`、`intermediate`、`advanced` |
| `prerequisites` | 可選 | 建議先讀的文章識別碼 |
| `relatedArticles` | 可選 | 相關文章識別碼 |
| `applicableVersions` | 發布前必填 | 適用的 C#／.NET 範圍；版本無關內容須明確標示 |
| `verifiedWith` | 有可執行範例時必填 | 實際驗證的 SDK、目標框架與必要語言版本 |
| `lastReviewed` | 發布前必填 | 最近人工確認內容正確性的日期 |
| `sources` | 發布前必填 | 支持文章說明的官方文件或其他可查核來源 |

另外記錄檔案的最後修改時間。修改時間與 `lastReviewed` 分開呈現，避免排版修改被誤認為技術內容已重新驗證。

學習路徑以標題、目標讀者、學習目標與排序後的 `articleId` 清單維護，建置時檢查引用是否存在。

### 4.2 文章模板

每篇文章以單一概念或問題為範圍，依下列順序編寫；不適用的小節可以省略。

1. 摘要：讀完後能理解或完成什麼。
2. 概念與用途：解釋核心概念及適用情境。
3. 先備知識與版本：指出必要背景與適用範圍。
4. 最小範例：提供程式碼、執行方式與預期輸出。
5. 實務情境：說明如何在真實專案使用。
6. 常見錯誤：說明錯誤的原因與修正方式。
7. 相關知識：連結下一步與相近概念。
8. 參考來源：附上可查核的文件連結。

### 4.3 內容品質

- 中文術語首次出現時，附上必要英文名稱，例如「非同步（asynchronous）」。
- 程式碼保留正確的 API 名稱，複製後不混入行號或說明文字。
- 承諾可直接執行的範例，放入 `examples/csharp/` 並以宣告的環境驗證；示意片段則標明上下文。
- 範例應顯示預期輸出，或清楚說明可觀察的行為。
- 語言、平台與框架的版本需求分別記錄。
- 來源以 Microsoft Learn 等官方資料為優先，編寫原創說明與範例。
- 草稿放在公開內容集合之外，完成審閱後才進入發布範圍。
- 發布前檢查內部連結、文章識別碼、版本資訊與內容完整性。

## 7. 技術架構與專案組織

### 7.1 技術選型

| 項目 | 決策 | 理由 |
| --- | --- | --- |
| 網站框架 | Astro＋Starlight | 以內容站為基礎，沿用成熟的文件閱讀介面 |
| 程式語言 | TypeScript，開啟嚴格型別檢查 | 驗證文章資料與自訂互動功能 |
| 內容來源 | Markdown；需要互動內容時使用 MDX | 易於編寫、審閱與 Git 版本管理 |
| 全文搜尋 | Pagefind | 建置時產生索引，搜尋在瀏覽器執行 |
| PWA | Web App Manifest＋Service Worker | 提供安裝與離線能力 |
| Service Worker 建置 | `workbox-build` 獨立建置步驟 | 明確控制產物、資源清單與快取策略 |
| 套件管理 | pnpm | 統一安裝流程與 lockfile |
| 內容紀錄 | Git | 保留修改歷史，支援審閱與回復 |
| 發布 | HTTPS 靜態託管＋CI | 每次發布產生可重現的完整產物 |
| 未來本機個人資料 | IndexedDB，第二階段導入 | 儲存收藏、閱讀進度與知識包狀態 |

Starlight 預設以 Pagefind 提供全文搜尋；中文斷詞需要確認使用 Pagefind 的 extended 發行版本，並以實際文章驗證查詢效果。[Starlight 搜尋](https://starlight.astro.build/guides/site-search/)、[Pagefind 語言支援](https://pagefind.app/docs/multilingual/)。

Workbox 可透過 `generateSW` 產生 Service Worker，或以 `injectManifest` 將預快取清單加入自訂 Service Worker。首期先以簡單快取需求評估 `generateSW`，增加知識包等自訂邏輯時再評估 `injectManifest`。[Workbox 建置文件](https://developer.chrome.com/docs/workbox/modules/workbox-build)。

版本相容性檢查列為實作前置工作。2026-10-07 查核時，`@vite-pwa/astro` 的主分支套件宣告列出 Astro 1 至 5 的 peer dependency 範圍，因此本規劃採用獨立 Workbox 建置流程；若後續改用整合套件，需重新確認當時的相容版本。[套件宣告](https://github.com/vite-pwa/astro/blob/main/package.json)。

### 7.2 架構圖

```mermaid
flowchart LR
    A[Markdown／MDX 文章] --> B[內容驗證]
    B --> C[Astro／Starlight 靜態建置]
    C --> D[Pagefind 搜尋索引]
    D --> E[Workbox 產生 Service Worker]
    E --> F[完整發布產物]
    F --> G[HTTPS 靜態託管]
    G --> H[瀏覽器／PWA]
```

### 7.4 可重現開發

- 在 `package.json` 宣告實際使用的 pnpm 版本，並固定相容的 Node 版本。
- 以 `pnpm-lock.yaml` 管理依賴，CI 使用 `pnpm install --frozen-lockfile`。
- 採用 ESM，讓本機與建置腳本使用一致的模組系統。
- 建立適用的 `dev`、`build`、`preview`、`lint`、`typecheck`、內容檢查與測試入口。
- `build` 完成頁面、搜尋索引與 Service Worker 的完整流程。
- 實作啟動時選定並記錄 Astro、Starlight、Pagefind 與 Workbox 的相容版本。

## 8. PWA 與離線策略

### 8.1 安裝與基本能力

Manifest 設定網站名稱、圖示、啟動網址、顯示模式與主題色，並提供 192px、512px 圖示及適合平台使用的圖示資源。正式環境以 HTTPS 提供服務，開發環境使用 localhost。[MDN PWA 安裝說明](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable)。

安裝提示依平台能力呈現；行動裝置提供對應的安裝操作說明。Service Worker 負責離線資源的讀取與更新，快取規則依資源用途制定。[MDN 快取說明](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Caching)。

### 8.2 首期快取策略

| 資源 | 策略 | 讀者可見的行為 |
| --- | --- | --- |
| 基本樣式、腳本、圖示與離線頁 | 建置時列入預快取清單，依內容版本更新 | 成功準備後，離線仍能開啟閱讀介面 |
| 文章 HTML | 優先網路；失敗時使用成功快取的版本 | 有網路時取得新內容，離線閱讀已快取文章 |
| 文章所需圖片與其他本站資源 | 快取已閱讀文章的必要資源，設定數量與容量上限 | 完整快取後才標示文章離線可用 |
| Pagefind 搜尋資源 | 首期提供線上搜尋；完整離線搜尋納入知識包 | 離線時明確顯示搜尋範圍與限制 |
| 外部網站、來源連結與嵌入內容 | 顯示外部資源提示 | 離線文章仍可閱讀本站內容，外部連結於連線後開啟 |

必要字型、樣式、腳本與文章圖片以可在本站快取的資源為優先。大型附件另外處理，容量上限與保留文章數量在效能驗證時確定。

預快取清單只納入基本介面、離線頁與必要靜態資源；文章 HTML 由上述執行期快取規則處理。搜尋資源依建置版本區分網址或快取識別，避免新版文章與舊版索引混用。

首次閱讀文章時，確認 Service Worker 已能控制頁面，並完成文章與必要資源的快取，再顯示「可離線閱讀」。未快取文章應顯示清楚的離線提示。

網站採用多頁靜態網址，離線處理應保留各文章路由與 404 行為；無快取的文章導向離線說明，不將不同文章一律回傳為首頁。

### 8.3 更新與版本一致性

1. 每次建置產生識別版本，發布同一版本的 HTML、資源與搜尋索引。
2. 新版 Service Worker 準備完成後，顯示更新提示。
3. 讀者選擇更新後再切換版本並重新載入，保留當前文章網址。
4. 舊頁面使用的資源保留至切換完成，再依生命週期清理舊快取。
5. 第二階段的知識包另以版本管理，確認新包完整後再替換舊包。

離線搜尋的索引與資源必須來自同一版知識包，避免索引指向尚未下載或已改版的文章。

### 8.4 第二階段：C# 離線知識包

- 產生包含文章、必要資源、C# 專用搜尋索引與檔案版本資訊的下載清單。
- 下載前顯示文章數量、版本與預估大小。
- 提供下載進度、取消、重試、刪除與更新操作。
- 驗證所有必要資源完整後才標示下載完成。
- 中斷時保留可重試狀態；更新失敗時仍能閱讀既有完整版本。
- 在可用時查詢裝置儲存容量，並處理空間不足或快取被清除的狀況。

## 9. 編寫、審閱與發布流程

```mermaid
flowchart LR
    A[建立草稿] --> B[撰寫內容與範例]
    B --> C[內容審閱與範例驗證]
    C --> D[移入發布內容集合]
    D --> E[Git commit／審閱]
    E --> F[CI 檢查與預覽]
    F --> G[確認正式發布]
```

主維護者可以自行完成審閱；若增加共同作者，透過 Pull Request 審閱後合併。依功能、文件與設定等意圖建立可讀的 commit。

建置檢查包含必填欄位、重複識別碼、重複網址、無效內部連結、無效學習路徑引用與應排除的草稿。

正式發布保留可回復的上一版產物。回復時同步處理 Service Worker 與快取版本，使重新連線的讀者能切換到回復版本。

技術內容以每季檢視一次為初始維護節奏，重大版本變更或讀者回報問題時提前修正。外部來源失效以定期檢查處理，避免偶發網路失敗阻擋每次建置。

## 10. 測試與驗收

### 10.1 驗證策略

| 風險或行為 | 適用防線 | 驗證內容 |
| --- | --- | --- |
| 無效文章資料與連結 | schema、內容檢查與建置 | 重複 ID、無效網址、遺失來源、引用不存在的文章 |
| TypeScript 與程式碼品質 | 型別檢查與 lint | 自訂元件與建置腳本的靜態錯誤 |
| 有分支的純邏輯 | 少量單元測試 | 版本判定、下載狀態轉換等真正需要驗證的規則 |
| 自訂閱讀互動 | 整合測試 | 目錄、更新提示、操作後可見的狀態與錯誤提示 |
| 搜尋到文章 | 關鍵流程 E2E | 查詢 → 結果 → 正確文章與可直接重新開啟的網址 |
| PWA 離線閱讀 | 使用正式建置的 E2E | 快取完成 → 斷網 → 重新開啟文章 → 讀取必要資源 |
| PWA 更新 | 使用兩個發布版本的 E2E | 偵測新版 → 提示 → 更新 → 內容與資源版本一致 |
| 安裝與實際行動裝置體驗 | 裝置人工驗收 | Android Chrome、iOS Safari 的操作與離線行為 |
| 可執行 C# 範例 | 編譯與執行檢查 | 在宣告環境執行，結果符合文章說明 |

測試以讀者可觀察的行為為準。以最小且適合的層級處理風險，避免重複驗證純展示元件或以覆蓋率數字取代重要流程。

Astro 文件頁以建置、內容檢查與少量跨頁 E2E 為主要防線；自訂互動元件再加入整合測試。若採用 React／Vue 元件，依元件責任選擇對應 Testing Library。

### 10.2 首期驗收清單

- [ ] 首頁、C# 主題入口與入門路徑可引導讀者找到目標文章。
- [ ] 15 篇核心文章完成審閱，具摘要、範例或適當說明、版本資訊與來源。
- [ ] 文章網址可直接開啟與分享，內部連結與學習路徑引用皆有效。
- [ ] 「C#」「非同步」「async」「Task」「泛型」「nullable」等查詢能找到預期內容。
- [ ] 搜尋無結果時提供可理解的提示；離線時清楚說明搜尋能力。
- [ ] 360px 手機寬度下，正文與頁面不產生非預期的橫向溢出。
- [ ] 導覽、搜尋與主要操作可用鍵盤完成，焦點狀態清楚。
- [ ] 深淺色模式下，文字與程式碼清楚可讀。
- [ ] Chrome／Edge／Safari／Firefox 完成主要閱讀流程驗證；安裝依平台能力驗收。
- [ ] 支援的平台可完成 PWA 安裝，圖示、名稱與啟動網址正確。
- [ ] 成功快取的文章在斷網後可以重新開啟，必要圖片與樣式正常。
- [ ] 未快取文章在斷網時顯示離線說明。
- [ ] 新版提示與更新流程可用，更新後文章與資源保持一致。
- [ ] lint、型別檢查、內容檢查、適用測試與正式建置皆通過。
- [ ] 可在乾淨環境以宣告的 Node／pnpm 與 lockfile 重現建置。
- [ ] 正式發布與回復步驟已有操作紀錄或文件。

首版另訂內部效能目標：代表性文章在固定的行動測試條件下，LCP 目標不超過 2.5 秒、CLS 不超過 0.1。這是初始工程目標，實作時記錄裝置、網路與測量方式；以三次測量的中位數評估，避免將單次分數視為保證。

## 12. 維運與擴充

| 情境 | 對應方向 |
| --- | --- |
| 新增程式語言 | 新增主題內容，沿用文章模型與閱讀介面 |
| 新增框架或平台 | 使用對應分類，透過相關文章與路徑連結既有概念 |
| 搜尋內容增加 | 評估索引大小、搜尋排序與主題篩選，再決定是否更換搜尋方案 |
| 增加共同作者 | 先使用 Git／Pull Request 審閱流程 |
| 需要網站直接編輯 | 評估 CMS 或 ASP.NET Core API，加入草稿、權限與修訂紀錄 |
| 需要跨裝置同步 | 導入帳號與同步 API，為本機個人資料設計同步與衝突處理 |
| 需要私人內容 | 在公開靜態產物之外設計受權限保護的內容來源與閱讀流程 |

若導入後台，內容 API 需提供穩定識別碼、版本與發布狀態，讓既有閱讀端可逐步改接新來源；相應的資料庫模型與 migration 在該階段另行規劃。

維運成本分為網域、靜態託管、CI、內容維護，以及未來的後台與資料庫。具體費用於選定平台後依當時方案估算，首期先控制必要的外部服務數量。

## 13. 主要風險與處理方式

| 風險 | 影響 | 處理方式 |
| --- | --- | --- |
| 文章缺少版本資訊 | 讀者在不同環境使用範例時失敗 | 記錄適用版本與實際驗證環境 |
| 中文與技術符號搜尋效果不足 | 文章難以找到 | 確認中文斷詞版本，建立代表性查詢的驗收案例 |
| 只快取 HTML，必要資源未完成 | 文章離線後呈現不完整 | 資源完整檢查通過後才顯示離線可用 |
| 快取與新版索引不一致 | 搜尋連到錯誤或缺少的內容 | 採同版建置、更新提示與版本化知識包 |
| 裝置空間不足或資料遭清除 | 離線文章或本機收藏不可用 | 顯示實際狀態，提供重新下載；個人資料後續可增加匯出 |
| 套件版本不相容 | 建置或 PWA 整合失敗 | 鎖定相容版本、保留 lockfile、使用獨立 PWA 建置流程 |
| 內容擴充後分類失去一致性 | 重複文章或讀者無法定位概念 | 遵循主題、分類、標籤與學習路徑的責任分工 |
| 維護工作超出個人負荷 | 文章長期未更新 | 控制首期範圍，保留最近審閱日期，逐步增加主題 |
